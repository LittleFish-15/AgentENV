# Host pmem/DAX 按需装载设计

基线：本地09c0e602fa2f48b6ab345e013dfafbee08f8287f，对应全量公开核心782577411ff20522d33c22dffb533e9678334fed。独立分支feat/host-pmem-demand；不修改全量分支、运行服务、既有对象或原版报告。

## 目标与不能混淆的量

Guest rootfs产生实际后备读请求时，才将对应不可变lower的块装入UB。两节点复用同一个已发布块，Host经OBMM只读卷与FS-DAX read_iter消费；写入仍走本地upper。不能回退到普通文件读取并将其称作UB命中。

必须分别记录请求有效字节、实际装载payload、逻辑镜像长度、唯一活跃UB容量及可证实的新增物理量。按需不自动改变SDK分配粒度。已审查UBSE源含128MiB对齐、默认块大小和最小导入配置，调度器按节点GetBlockSize取整；现有64MiB请求映射128MiB与此一致。这不证明所有可能配置的绝对下限，但未经新的平台验证，不能承诺64MiB小例子降到128MiB以下。

## 为什么不直接复用可写缓存池

当前已验证OBMM前端对整个区域做不可逆只读封存。一个已挂载供DAX读取的区域不能重新可写填充，也不能让存在读者的slot被新内容覆盖。已有stored-direct的可写UB slot缓存不能直接冒充Host DAX按需版本。

初版复用原内核ABI，不加载新模块：每个缓存块拥有独立的不可变小文件系统发布，装载、校验完成后再封存和挂载；回收须各节点先释放视图/FD/导入，最后删除全局对象。不在已发布区域上就地写入或复用slot。

## 粒度与容量策略

默认规划一个128MiB逻辑发布镜像，其中payload块上限120MiB，余量用于文件系统元数据。该值是容量规划，不是现场硬配额；构建必须实际验证文件系统可容纳，SDK映射后仍要核容量。配置可以选择其他已验证粒度，但禁止拿4KiB请求当4KiB UB分配。

64MiB文件在此初版中可能仍触发一个128MiB发布，所以不会宣称该例子已降低占用。对于GiB级lower集合，只有触及的块驻留；收益取决于触及块数、对齐、元数据、读放大和缓存上限。例如只访问少数块时可以避免全量装入，但随机触及所有块时仍可能接近全量甚至更贵。

不对每个4KiB请求分配一个128MiB对象。默认无跨块预取；同块并发miss合并成一次装载。预算按已知覆盖的保守收费和在途预留执行，不宣称平台物理硬限额。

## 数据路径

1. 准备期生成可信不可变manifest：文件总digest/长度、块偏移/长度/digest、块大小及版本；不创建UB对象。可离线扫描源文件，不能把准备期读取算成Guest访问。
2. Guest→ublk/OverlayBD→按需DAX broker，依据layer digest及offset切分跨块请求。
3. 单一发布协调器按manifest identity+layer digest+chunk offset合并A/B请求，持久化FILLING意图后调用发布后端。READY表示不可变UB后备发布完成，不表示任何节点的DAX视图已验收；节点取得读票后仍须完成本地OBMM封存/挂载和FD核验。
4. 发布后端只读取该块。源读取必须使用受支持O_DIRECT、精确范围与块摘要校验；没有direct支持就失败，不自动转buffered。暂存和格式化成本、可能残留文件缓存必须单列并核验。
5. 构建该块的不可变小文件系统镜像，经已有SDK→只读FD→OBMM卷→Host DAX路径发布。接收端确认实际S_DAX/readonly、文件长度与块摘要；不执行整份lower的全量verify_mapping，否则一次打开就会触发全量加载。
6. 读取只使用该块DAX文件的pread。请求结束关闭读取视图/FD后归还全局读票；长生命周期的被动挂载仍登记为已附着节点。
7. 预算不足时显式选择没有活跃读票的LRU块退役。所有附着节点确认视图和导入已退出、全局对象删除确认后才释放预算。未知结果、断连或超时不等于退出。

## 生命周期与故障

ABSENT→FILLING→READY→RETIRING→ABSENT。装载/删除结果不确定进入UNCERTAIN，保留预算和身份，禁止换名字盲目重试。调用前持久化对象名和generation。READY才可发读票；相同generation的读票只能显式释放一次，旧generation不能操作新对象。

节点租约不是超时租约：进程死亡、网络超时不能自动消除pin。重启协调器不能清空旧journal；发现旧事务时必须显式核对双方引用，初版拒绝隐式恢复。全量方案继续独立运行，不被cache eviction触及。

## 实现边界与验收

本分支先实现manifest/按需范围规划、单次fill协调与容量/读票状态机、只接受真实DAX FD的按需读取适配；后端必须实现发布、节点视图和跨节点退役合同，不能用普通文件或Python内存模型作正式后端。该核心组件的本地模型测试只验协议，不证明两节点硬件能力或节省。

仍需接合并验收：每块文件系统镜像构建、真实SDK发布器与root helper、双节点控制传输及鉴权、普通broker FD交接、Runtime严格绑定、Native构建和目标机实验。这些未接合前不提供“可部署完整按需版”的承诺。

原kernel frontend、全量broker与全量CLI没有改动。初版没有默认网络/本地文件假后端：真实节点view_controller和view_factory未配置时必须拒绝分配/读取。它们需要接合root mount/FD服务及两节点自动控制通道，这部分尚未实现。人工逐次中转不能服务Guest每一次miss，因此发布前必须设计并批准运行期间的节点间协调端点/鉴权，而不是让用户逐块转token。

当前不能把本分支称为已经部署或已完成两节点按需demo。后续交付顺序是补齐真实node视图控制与传输、接合broker/Runtime、做Linux原生验证，最后才和保留全量版本做同负载比较。该状态表区分代码未接合与平台粒度约束。

比较使用原版/全量DAX/按需DAX三个明确实现，先复用同一模板和轨迹。记录首次miss延迟、命中延迟、装载字节/请求字节、UB活跃容量峰值、退役次数及缓存抖动；共享计费只按唯一发布对象，导入不计第二份。全量基线不重编译、不修改、不释放现有对象。任何新GiB级预算与服务变更另列具体执行范围后由用户中转。
